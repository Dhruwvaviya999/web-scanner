Part 1

Get it running

Three things run at once: the database, the backend API, and the web UI. Start them in that order. You only do steps 1–4 once.

  1. Start PostgreSQL

    It should already be running as a system service on port 5432. If the backend later says it cannot connect, this is the first thing to check.

  2. Set up the backend once

    # from the project root
cd backend

# 1. make a virtual environment (Python 3.12+)
python -m venv .venv
.venv\Scripts\activate          # Windows
# source .venv/bin/activate     # macOS / Linux

# 2. install dependencies
pip install -r requirements.txt

# 3. configuration
copy .env.example .env          # then edit it

    Open .env and set two values: DATABASE_URL (your Postgres connection string) and JWT_SECRET_KEY. Generate the key rather than inventing one:

    python -c "import secrets; print(secrets.token_urlsafe(64))"

  3. Create the database tables

    alembic upgrade head

    This runs every migration in order, up to 0015_path_security. Never change the schema by editing the database directly — always write a migration.

  4. Start the backend

    uvicorn app.main:app --reload --port 8000

    Now visit localhost:8000/docs. That is the interactive API explorer, and it is the fastest way to poke at anything. Health check lives at /api/health.

  5. Start the frontend

    # in a second terminal, from the project root
cd frontend
pnpm install
copy .env.example .env.local
pnpm dev

    Open localhost:3000, register an account, and you are in.

Part 2

Run your first scan

Only scan what you own

This tool sends real requests, and some of them are active probes. Point it only at a system you own or have written permission to test. Unauthorised scanning is illegal in most countries. When you are experimenting, use the local fixtures described below.

The safe way to practise

The test suite already builds small deliberately-vulnerable apps that run on localhost and disappear when the test ends. Watching one of those run is the best possible introduction:

# see the path-traversal detector find a planted bug
.venv\Scripts\python -m pytest tests/test_path_security.py -v

# or the whole suite (about two minutes)
.venv\Scripts\python -m pytest

Scanning from the UI

On the dashboard, paste a URL and start a scan. The scan runs inline, so the request stays open until it finishes. When it is done you get three views: Findings (what is wrong), Attack surface (what was discovered), and Report (the full picture, with coverage).

Scanning from the API

Everything the UI does is a plain HTTP call. Log in first — the session is a cookie — then create a scan:

POST /api/scans
{ "target_url": "https://your-own-site.example" }

Useful reads afterwards, where {id} is the scan id:

EndpointGives you
GET /api/scans/{id}Status, timing, and the summary counters
GET /api/scans/{id}/findingsEvery finding, grouped by rule
GET /api/scans/{id}/endpointsURLs and parameters the crawler found
GET /api/scans/{id}/api-endpointsThe API surface, from Phase 13
GET /api/scans/{id}/formsForms found (never submitted)
GET /api/scans/{id}/reportThe canonical report, including coverage
GET /api/scans/{id}/report/jsonThe same report as a download
POST /api/scans/{id}/cancelAsk a running scan to stop
Part 3

What happens during a scan

One scan runs eleven stages in a fixed order. Each stage adds to a single shared ScanReport, and later stages read what earlier ones found. That is why the order matters.

  1. auth_checkno traffic unless configured Confirms your credentials work before a crawl is spent on them.
  2. http_probesends One request to the target. Records status, headers, cookies, redirects.
  3. crawlersends Walks the same origin, bounded by pages, depth and a time budget. Finds URLs, parameter names and forms.
  4. endpoint_analysisreads Runs the header and cookie rules over everything the crawl captured.
  5. api_discoverysends Classifies which endpoints behave like APIs; fetches OpenAPI docs if published.
  6. active_scanprobes Runs the registered detectors — reflected XSS and SQL injection — against discovered parameters.
  7. authorizationsends Compares what different identities can reach, against a policy you supply.
  8. api_securityreads Sensitive field names, verbose errors, unsafe CORS — all from responses already fetched.
  9. session_securityreads Session cookies, tokens in URLs, JWT metadata, CSRF posture. Sends nothing.
  10. config_securitysends Transport and HSTS, plus a small fixed list of deployment paths. No brute-forcing.
  11. path_securityprobes Tests file/path parameters for directory traversal, using a harmless canary.
Findings all go to one place

No stage keeps its own list. Every stage hands findings to the shared aggregator, which deduplicates them by rule + subject and attaches an occurrence per affected endpoint. That is why the same problem on ten pages is one finding with ten occurrences, not ten findings.

Part 4

Where the code lives

The scanner is deliberately isolated. Nothing under app/scanner/ imports the database, the routers or the models — it speaks in plain dataclasses, and scan_service.py is the only translator. Keep it that way and everything stays testable without a database.

scanner/crawler/Bounded crawl, URL rules, HTML parsing
scanner/security/Header and cookie rules; the finding vocabulary
scanner/active/Probe engine, budget, comparison helpers
scanner/vulnerabilities/XSS and SQLi detectors
scanner/api/ · api_security/API discovery, then API weaknesses
scanner/session_security/Cookies, JWTs, CSRF verdicts
scanner/config_security/Transport, deployment files, CSP quality
scanner/path_security/Traversal and file inclusion
scanner/auth/ · authorization/Target credentials and access policy
scanner/analysis/The aggregator that deduplicates findings
app/reporting/Rows → the canonical report
app/core/config.pyEvery setting and budget

Every phase has the same four parts

Once you have read one module you have read them all. Open scanner/session_security/ and you will find exactly this shape:

FileJob

Part 5

Add your own check

Two routes, depending on whether your check needs to send anything.

The easy one: a new passive rule

Say you want to report a missing Cross-Origin-Opener-Policy header. That is four small edits and no migration.

  1. Add the rule name

    In scanner/security/types.py, add a member to FindingRule. Rules are a validated string, not a database enum — so adding one needs no migration. Only a new FindingCategory does.

    SECURITY_HEADER_COOP_MISSING = "SECURITY_HEADER_COOP_MISSING"

  2. Write the check

    In scanner/security/headers.py, next to the checks already there:

    def _check_coop(headers) -> list[FindingData]:
    if _header(headers, "cross-origin-opener-policy") is not None:
        return []
    return [FindingData(
        rule=FindingRule.SECURITY_HEADER_COOP_MISSING,
        title="Cross-Origin-Opener-Policy not set",
        category=FindingCategory.SECURITY_HEADER,
        severity=FindingSeverity.LOW,
        confidence=FindingConfidence.HIGH,
        description="...",
        evidence="No Cross-Origin-Opener-Policy header was present.",
        impact="...",
        remediation="Send Cross-Origin-Opener-Policy: same-origin.",
    )]

  3. Call it

    Add one line inside analyze_security_headers, in the document-only block with the other page-scoped headers.

    findings.extend(_check_coop(headers))

  4. Test it both ways

    In tests/test_security_headers.py, one test that it fires when the header is missing, and — more important — one that it stays silent when the header is present.

    .venv\Scripts\python -m pytest tests/test_security_headers.py

The bigger one: an active detector

If your check needs to send requests, write a detector instead. It must satisfy exactly two methods, and it never gets a HTTP client of its own — it is handed a ProbeEngine, which is what enforces scope, SSRF checks, redirect limits and the request budget.

class MyDetector:
    name = "my_check"

    def eligible(self, target) -> Eligibility:
        # pure and cheap. no I/O here.
        if target.method.upper() != "GET":
            return Eligibility.no("non_get_method")
        return Eligibility.yes()

    async def probe(self, target, engine) -> Sequence[DetectorObservation]:
        outcome = await engine.send(ProbeRequest(...))
        # interpret, then return (url, FindingData) pairs
        return []

Then register it in _active_detectors() in services/scan_service.py, behind its own *_ENABLED setting. Nothing else needs to change — the pipeline and the persistence layer already handle any detector.

When do I need a database migration?

Only for two things: a new FindingCategory (it is a native Postgres enum, so it needs ALTER TYPE inside an autocommit_block()), or new coverage columns on scans. New rules never need one.

alembic revision -m "describe the change"
alembic upgrade head
alembic downgrade -1     # always test the way back
alembic upgrade head
Part 6

Reading a finding

Every finding carries a severity and a confidence, and they answer different questions. Severity is how bad if real. Confidence is how sure we are. A HIGH/LOW is a guess about something serious; a LOW/HIGH is a certainty about something small.

CRITICAL

Almost never used. Most phases are forbidden from emitting it, because the scanner observes structure rather than confirming exploitation.

HIGH

Demonstrated or strongly-evidenced. A reproduced traversal canary, an exposed .env, a reachable .git directory.

MEDIUM

Real weakening, impact depends on context. A missing CSP, a CSP that lets script load from anywhere.

LOW

Worth fixing, small blast radius. Directory listing, a published source map, HSTS without includeSubDomains.

INFO

Inventory and unanswered questions. A Server header. “Session expiry could not be determined.” Not accusations.

Read the coverage before you trust the silence

Every report carries coverage counters, and several have a coverage_complete flag. When it is false, a budget ran out or a baseline was unusable — so the things that were not checked established nothing. An empty findings list on an incomplete scan is not a clean bill of health, and the report is written to say so.

Part 7

The rules this codebase lives by

Every phase follows these. If your addition follows them too, it will fit; if it does not, it will feel wrong in review.

01
Observe, classify, correlate, report.

In that order, and stop at the point the evidence stops.

02
Unknown stays unknown.

A missing Max-Age is not “the session never expires”. A form with no CSRF token is not “CSRF is exploitable”. Say what you saw.

03
Not-checked is never the same as safe.

Anything a budget skipped is recorded as skipped, and surfaced.

04
Never store a value.

Names, counts, statuses, media types — yes. Cookie values, tokens, file contents, credentials, response bodies — never. The database schema is built so there is nowhere to put them.

05
One transport, one budget.

Every request goes through HttpFetcher. That is the single place SSRF and same-origin rules are enforced, so no new code can escape them.

06
Prove the negative.

For every test that a check fires, write one that it stays quiet. The false-positive tests are the ones that make the tool usable.
